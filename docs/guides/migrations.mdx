pgb 2.0 ships its own migration engine (see [the 2.0 plan](#the-20-plan)). Until then the story is deliberately boring: three artifacts move together in every schema change, or none of them do.

1. **Live database** — evolved by versioned `.sql` migrations.
2. **`schema.sql`** — the declarative snapshot pgb parses. Codegen reads this file, never the live catalog.
3. **Generated `db/` package** — regenerated from `schema.sql` on every change.

If migrations and `schema.sql` move apart, pgb happily generates code for a database that no longer exists — every rule on this page exists to keep that from merging.

## The recommended loop

Use goose or golang-migrate for the live database. Both are plain versioned SQL files, both embed into the binary, and both stay out of codegen's way. goose with an embedded filesystem:

```go
package main

import (
	"context"
	"embed"
	"os"

	"github.com/jackc/pgx/v5/pgxpool"
	"github.com/jackc/pgx/v5/stdlib"
	"github.com/pressly/goose/v3"
)

//go:embed migrations/*.sql
var migrationsFS embed.FS

func migrate(ctx context.Context) error {
	pool, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
	if err != nil {
		return err
	}
	defer pool.Close()

	// goose speaks database/sql; pgx stdlib bridges
	db := stdlib.OpenDBFromPool(pool)
	defer db.Close()

	goose.SetBaseFS(migrationsFS)
	return goose.Up(ctx, db, "migrations")
}

```

The per-change loop — apply, mirror, regenerate, review:

```bash
# 1. apply the migration
goose -dir migrations postgres "$DATABASE_URL" up
# 2. mirror the same change
$EDITOR schema.sql
# 3. regenerate db/
sqlc generate
# 4. review the generated diff
git diff --stat db/
# 5. tests run against a migrated scratch DB
go test ./...
```

Commit the migration file, the `schema.sql` update, and the regenerated `db/` package in the same commit — the diff is the review artifact for all three.

<Tip>
Enforce step 3 in CI: `sqlc generate && git diff --exit-code db/` fails the build when someone commits a migration without regenerating. Drift then cannot merge instead of being discovered at runtime.
</Tip>

<Note>
golang-migrate works the same way: `000007_users_last_seen_at.up.sql` / `.down.sql` pairs served from `embed.FS` via the `iofs` source driver. Pick one tool and keep one migrations directory — mixing tools corrupts the version table.
</Note>

## A worked change: add a column

Add `last_seen_at` to `users`. One migration file:

```sql
-- +goose Up
ALTER TABLE public.users
    ADD COLUMN last_seen_at timestamptz;

-- +goose Down
ALTER TABLE public.users
    DROP COLUMN last_seen_at;
```

The matching `schema.sql` edit, in the same commit:

```sql
CREATE TABLE public.users (
    id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email         text NOT NULL UNIQUE,
    name          text NOT NULL,
    bio           text,
    metadata      jsonb,
    tags          text[],
    created_at    timestamptz NOT NULL DEFAULT now(),
    last_login_at timestamptz,
    last_seen_at  timestamptz
);
```

Run `sqlc generate`, and the diff shows every layer picking the column up on its own:

```diff
--- a/db/models.gen.go
+++ b/db/models.gen.go
@@ type User struct @@
     CreatedAt   pgtype.Timestamptz
     LastLoginAt pgtype.Timestamptz
+    LastSeenAt  pgtype.Timestamptz

@@ type UserFilter struct @@
     CreatedAfter *time.Time
+    LastSeenAfter *time.Time

@@ type UserSet struct @@
     LastLoginAt core.Set[pgtype.Timestamptz]
+    LastSeenAt  core.Set[pgtype.Timestamptz]
```

```diff
--- a/db/users.gen.go
+++ b/db/users.gen.go
@@ GetUser, ListUsers, UpdateUser, UpsertUser @@
-SELECT id, email, name, bio, metadata, tags, created_at, last_login_at
+SELECT id, email, name, bio, metadata, tags, created_at, last_login_at,
+       last_seen_at
```

The new field is immediately usable at every layer — model scan, filter, three-state set:

```go
stale, err := db.ListUsers(ctx, pool, db.UserFilter{
	LastSeenAfter: pgb.Opt(time.Now().Add(-30 * 24 * time.Hour)),
}, pgb.Limit(100))
```

```sql
SELECT id, email, name, bio, metadata, tags,
       created_at, last_login_at, last_seen_at
FROM public.users
WHERE last_seen_at > $1
LIMIT $2
```

Remember the index the new filter wants — see [indexes & performance](/docs/performance):

```sql
CREATE INDEX users_last_seen_at_idx ON public.users (last_seen_at);
```

## What not to do

<Warning>
Never hand-edit `db/*.gen.go`. Every file is overwritten by the next `sqlc generate`, so the edit is lost at best and silently diverged at worst. If the generated shape is wrong, the fix belongs in `schema.sql` or `sqlc.yaml` — the generator is the API.
</Warning>

<Warning>
Never let `schema.sql` drift from the live database. pgb parses `schema.sql` with the PG18 grammar; it does not introspect the catalog. A drifted file generates correct-looking code against columns and types that do not exist — the failure surfaces as runtime errors, not build errors. The same-commit rule and the CI check above are the guardrails.
</Warning>

<Warning>
Never edit a migration that has already been applied — the checksum no longer matches and every fresh environment fails to boot. Add a new migration that undoes or amends the change.
</Warning>

## Forward-compatible changes

Additive-first: prefer changes that old generated code and old binaries keep working against. The expanding/contracting pattern covers everything destructive:

| change | pattern |
|---|---|
| add a nullable column, or `NOT NULL DEFAULT` | additive — one migration, one regenerate, ship. `ADD COLUMN ... NOT NULL DEFAULT ...` is metadata-only since PG11 |
| add an index | additive — `CREATE INDEX CONCURRENTLY` on large tables (outside a transaction) |
| rename a column | expand/contract: add the new column, migrate + dual-write, regenerate so both fields coexist, switch readers, drop the old column in a later release |
| change a column type | expand/contract with a backfill migration — never `ALTER TYPE` in place on a hot table |
| drop a column | contract only: regenerate and deploy the build that no longer references it, then drop |

The rename sequence with pgb: the expanding migration adds `last_seen_at` alongside `last_login_at`; after `sqlc generate`, `UserSet` carries both fields, and the three-state sets (`pgb.Set` / `pgb.Null`) make the dual-write explicit in one statement; the contracting migration drops the old column once no deployed binary reads it. Each phase is a normal commit in the loop above.

<Note>
`schema.sql` is parsed with the PG18 parser — keep PG19-only DDL out of migrations and `schema.sql` until the [support matrix](/reference/support-matrix) marks PG19 as a supported target.
</Note>

## The 2.0 plan

The hand-run loop above is temporary. pgb 2.0 ([vision](/future/vision)) replaces it with a declarative schema DSL compiled into an encoded artifact, and `pgb migrate` (P2) becomes the executor:

```bash
pgb migrate dev      # diff artifact vs shadow DB → generate +
                     # auto-apply DDL to the dev database
pgb migrate deploy   # apply recorded migrations to staging/prod —
                     # explicit, no auto-diff
pgb migrate diff     # print the SQL plan without applying
pgb migrate status   # drift report: artifact vs live catalog
```

`pgb migrate status` is the drift check this page enforces by hand, promoted into the tool. goose and golang-migrate keep working — the generated `db/` package is unaffected by how DDL reaches the database.
