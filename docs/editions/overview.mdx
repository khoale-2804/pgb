pgb is not two products. It is **one compiler with two frontends**, and the split exists because SQL-first and toolkit-first developers want different entry points:

| | **sqlc plugin edition** | **standalone ORM edition** |
|---|---|---|
| ships as | `sqlc-gen-pgb` binary (process/WASM plugin) | Go module + `pgb` CLI (`go get`, `go install`) |
| schema source | your `schema.sql` via sqlc (+ pgb's own oliphant re-parse) | `schema.sql` / `pgb.schema` DSL via oliphant directly |
| handwritten queries | typed wrappers generated by sqlc analysis | `Raw()` escape hatch; typed wrappers via pgb's own analyzer (later) |
| generated output | **identical** | **identical** |
| runtime | **identical** `core/` | **identical** `core/` |
| right for | existing sqlc users, SQL-first teams | projects that want the ORM, migrations, and full type system without a sqlc dependency |

## Why one core works

Everything hard lives below the frontend boundary:

1. **SchemaIR** — the parsed, resolved schema (tables, columns, types, paradedb indexes, directives). Frontends only *build* it; nothing downstream knows where it came from.
2. **The codegen passes** — models, descriptors/builders, statics/search: three deterministic passes over the IR.
3. **The runtime core** — expression tree, SQL emitter, scan pipeline, DBTX. All generated code from both editions imports the same small module.
4. **The type system** — one Postgres→Go mapping, version-aware.

The proof is mechanical: the golden-file suite runs the **same schema through both frontends and requires byte-identical output**. If the editions ever drift, CI fails before a release does.

## Why the standalone core is the strategic one

The sqlc plugin protocol is a great distribution channel but a lossy ceiling: no SQL AST, `CREATE INDEX` dropped, extension functions untyped, release cadence out of pgb's hands. The standalone frontend controls its own catalog model — which is what makes the ORM edition's promises possible (full type matrix, planner-aware emission, migrations, relations). Crucially, the plugin already does most of this work: it re-parses schema files with oliphant for everything sqlc drops. The standalone edition is that parser promoted from a side-pass to the main entrance.

<Note>
Sequencing: v0.1 ships **plugin-only** (cheapest vertical slice, dogfoods the core against sqlc's analyzer). v0.2 extracts the standalone CLI/library — same golden output. v0.3+ adds the ORM layers (relations, migrations, DSL) on the standalone core per the [2.0 plan](/future/vision). The plugin frontend keeps tracking sqlc.
</Note>
