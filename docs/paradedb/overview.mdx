pgb targets **ParadeDB 0.25.9+ / 0.26-rc** — the v2 operator API (stable since 0.20.0). The current stable release is v0.25.9 (2026-09-11); v0.26.0-rc.1 is tracked but prerelease. The 0.26.0-rc changelog introduced no operator or `pdb.*` signature changes; its improvements (vector pushdown for RRF, tiebreak ordering with vector) benefit pgb's emitted hybrid-search SQL automatically.

<Note>
Both index spellings are accepted at DDL parse time: `USING paradedb` (0.25.0+) and the legacy `USING bm25` alias.
</Note>

## What "full support" covers

1. **DDL extraction** — the `USING paradedb` index definition is parsed from your schema ([details](/paradedb/index-ddl)) and drives codegen: which columns get search predicates, the `key_field` for scoring, tokenizer metadata.

   ```go
   // the .Description() descriptor exists only because description is in the index DDL
   rows, err := db.SearchProducts(ctx, pool, db.Products.Description().Match("trail running"), 10)
   ```

2. **Predicates** — typed methods emitting the complete v2 operator vocabulary ([reference](/paradedb/predicates)).

   ```go
   // emits: WHERE description @@@ 'runing'::pdb.fuzzy(2)
   rows, err := db.SearchProducts(ctx, pool, db.Products.Description().Fuzzy("runing", 2), 10)
   ```

3. **Scoring & snippets** — `pdb.score(key_field)`, `pdb.snippet*` families with named arguments ([reference](/paradedb/scoring)).

   ```go
   // rows[i].Score is populated from pdb.score(id)::float8 in the emitted SELECT
   rows, err := db.SearchProductsScored(ctx, pool, db.Products.Description().Match("shoes"), 10)
   ```

4. **Hybrid search** — the documented RRF fusion pattern as a generated function ([reference](/paradedb/hybrid-search)).

   ```go
   // one SQL statement: BM25 match + vector nearest neighbors fused with RRF
   rows, err := db.SearchProductsHybrid(ctx, pool, "trail running shoes", qvec, 10)
   ```

5. **Aggregations** — the `pdb.agg` JSON aggregation DSL ([reference](/paradedb/aggregations)).

   ```go
   // emits: SELECT pdb.agg(id, '<Elasticsearch-compatible JSON>') FROM products
   res, err := db.AggregateProducts(ctx, pool, db.Products.Agg().Terms("json_brand", 20))
   ```

6. **Tokenizers** — the full tokenizer/token-filter list, extracted from DDL casts ([reference](/paradedb/tokenizers)).

   ```go
   // sku::pdb.literal produces one token per value, so .Exact() rides the === family
   rows, err := db.SearchProducts(ctx, pool, db.Products.Sku().Exact("SHO-42"), 10)
   ```

7. **Architecture** — the LSM-tree index, custom-scan pushdown, and joins ([reference](/paradedb/architecture)).

   ```go
   // every generated search ends in ORDER BY ... LIMIT n, which rides SegmentedTopKExec
   rows, err := db.SearchProducts(ctx, pool, q, 10)
   ```

## Design implications for pgb

| feature | what pgb generates |
|---|---|
| one `USING paradedb` index per table | exactly one `SearchIndex` in the [SchemaIR](/architecture/schema-ir); a second index on the same table is a parse-time error |
| covering index (every field stored in-index) | predicates are generated only for indexed columns; widening the index is a rebuild and shows up as a regenerated-code diff |
| v2 operators are plain SQL | search SQL is emitted at runtime from `core/search.go` — sqlc never has to resolve `pdb.*` |
| `pdb.*` functions unknown to sqlc's analyzer | generated models stay typed; handwritten `.sql` needs a `::float8` cast or the database-backed analyzer ([handwritten queries](/guides/handwritten-queries)) |
| Top-K pushdown (`SegmentedTopKExec`) | generated search functions always carry `ORDER BY ... LIMIT n` — never an unbounded scored scan |
| join pushdown (DataFusion MPP) | generated join searches keep join keys, filter columns, and `ORDER BY` columns indexed, and always emit a `LIMIT` |
| transactional visibility (no refresh interval) | no refresh API to generate — a generated search sees its own committed writes immediately |
| `key_field` must be UNIQUE and first (upstream caveat) | parse-time warning; `pdb.score(key_field)` is emitted against the declared key field ([index DDL extraction](/paradedb/index-ddl)) |
| pgvector required dependency (since 0.25.0) | `vector` columns are indexed inside the same index (`embedding vector_cosine_ops`) and typed via pgvector in generated models |

## Single extension

pg_search is one Postgres extension, not a family: BM25 full-text, vectors, hybrid search, aggregates, joins, and OLAP all ship in it — Apache DataFusion is embedded inside and does the analytical work. The index lives inside Postgres (block storage API, buffer cache, WAL), stored alongside the table.

<Note>
Two corrections to older material: pg_analytics (archived 2025-03-19) and pg_lakehouse (discontinued) are history only, never current features. And there is no `USING columnar` table AM — "columnar" refers to the columnar/fast-field half of each LSM segment.
</Note>

## The version gate

```yaml
options:
  paradedb:
    version: "0.26"
```

All pg_search emission lives in one handwritten file, `core/search.go`, behind this gate. ParadeDB broke its API twice in 2025 (`paradedb.*` JSON DSL → `pdb.*` casts, `USING bm25` → `USING paradedb`); when it churns again, the fix is contained to that file.

## Where pg_search does *not* flow through sqlc

sqlc parses `@@@` fine (the real PG grammar accepts any operator), but `pdb.*` functions are unknown to its analyzer:

- **Generated layer** — unaffected. pgb emits SQL at runtime; the server validates it, not the codegen analyzer.
- **Handwritten `.sql` queries** — on sqlc v1.31.1 they fail analysis ("function does not exist"); on main they degrade to untyped `any` columns. Fixes: cast in SQL (`pdb.score(id)::float8`) or point sqlc's database-backed analyzer at a live ParadeDB (`database: {uri: ...}, analyzer: {database: true}`) so extension types resolve exactly. See [handwritten queries](/guides/handwritten-queries).
